Yes. The important distinction is that the gray block in your screenshot is not generated by Gradle. It is IntelliJ rendering declarations that a Kotlin compiler frontend plugin (FIR) has synthesized.

kotlinx.serialization is doing essentially what you want. The Kotlin docs explicitly use serialization as the example: its frontend generates the companion object and serializer() declaration, then its backend supplies the implementation. Frontend-generated declarations participate in name/type resolution and can therefore be visible to the IDE. Kotlin

So for:

Kotlin
@Validatable
data class User(
    val name: String,
    val age: Int,
)

you want the compiler frontend to behave as though this existed:

Kotlin
data class User(...) {
    companion object {
        fun metadata(): Metadata<User>
    }
}

Then:

Kotlin
val metadata = User.metadata()

works naturally, because User.metadata() is effectively User.Companion.metadata().

The architecture you want

Your plugin should have three pieces:

PieceResponsibility
Gradle pluginAdds/configures your compiler plugin
FIR compiler pluginDeclares Companion + metadata()
IR compiler pluginGenerates the actual implementation/body

The gray IntelliJ preview then comes from the FIR declaration, not from custom UI code you write yourself.

Kotlin's official compiler-plugin template uses this same split: :compiler-plugin, :plugin-annotations, and :gradle-plugin. GitHub

1. Generate the declaration with FirDeclarationGenerationExtension

The key extension is:

Kotlin
FirDeclarationGenerationExtension

It exists specifically for synthesizing classes, functions, properties, constructors, etc. Kotlin+1

For your case, conceptually your FIR extension does this:

@Validatable class User
          │
          ▼
Does User already have a companion?
          │
     ┌────┴────┐
     │         │
    no        yes
     │         │
generate      use
Companion     existing Companion
     │         │
     └────┬────┘
          ▼
 generate metadata(): Metadata<User>

The FIR docs specifically say that to generate a companion for an outer class, the declaration generation extension should generate the corresponding outerClassId.Companion. GitHub

This is also exactly how serialization behaves: if there is no companion, it generates one; if there is already a companion, it only generates serializer(). GitHub

So make yours follow the same rule:

Kotlin
@Validatable
class A

becomes conceptually:

Kotlin
class A {
    companion object {
        fun metadata(): Metadata<A>
    }
}

while:

Kotlin
@Validatable
class B {
    companion object {
        fun somethingElse() {}
    }
}

becomes conceptually:

Kotlin
class B {
    companion object {
        fun somethingElse() {}

        // synthesized
        fun metadata(): Metadata<B>
    }
}

2. Register your FIR extension

Your K2 registrar will look roughly like this:

Kotlin
class ValidatableFirRegistrar : FirExtensionRegistrar() {

    override fun ExtensionRegistrarContext.configurePlugin() {
        +::ValidatableDeclarationGenerator
    }
}

This is exactly the registration style used by the official compiler-plugin template. GitHub

Then connect the FIR frontend and IR backend through CompilerPluginRegistrar:

Kotlin
class ValidatableCompilerPluginRegistrar : CompilerPluginRegistrar() {

    override val pluginId: String =
        "com.example.validatable"

    override val supportsK2: Boolean =
        true

    override fun ExtensionStorage.registerExtensions(
        configuration: CompilerConfiguration
    ) {
        FirExtensionRegistrarAdapter.registerExtension(
            ValidatableFirRegistrar()
        )

        IrGenerationExtension.registerExtension(
            ValidatableIrGenerationExtension()
        )
    }
}

The official template has almost exactly this setup: it registers a FIR registrar and an IrGenerationExtension from the compiler plugin registrar. GitHub

3. Your FirDeclarationGenerationExtension

The exact APIs change between Kotlin releases, so I wouldn't copy a full implementation from a random GitHub project. Kotlin explicitly warns that the compiler plugin API is unstable and can break every release. Kotlin

But the shape should be something like this:

Kotlin
class ValidatableDeclarationGenerator(
    session: FirSession
) : FirDeclarationGenerationExtension(session) {

    companion object {
        val METADATA_NAME = Name.identifier("metadata")
    }

    object Key : GeneratedDeclarationKey()

    /*
     * 1. Find classes annotated with @Validatable.
     *
     * 2. If there is no companion:
     *       advertise/generate ClassId = ownerClassId.Companion
     *
     * 3. For that companion:
     *       advertise `metadata` as a callable name
     *
     * 4. Generate:
     *
     *       fun metadata(): Metadata<OwnerClass>
     */
}

The current official template is useful here because it shows the modern helpers such as:

Kotlin
GeneratedDeclarationKey
createMemberFunction(...)
createConstructor(...)

and the current MemberGenerationContext APIs. GitHub

One detail is especially important for the IntelliJ experience: make the declarations actual plugin-generated FIR declarations, with your GeneratedDeclarationKey / plugin origin. Don't simply mutate FIR or create unrelated IR declarations later.

4. Then implement the body in IR

FIR only needs to tell the compiler:

Kotlin
fun metadata(): Metadata<User>

The body can be supplied later by your IrGenerationExtension:

Kotlin
fun metadata(): Metadata<User> {
    return Metadata(
        // information collected from User
    )
}

The FIR docs explicitly say generated function bodies can be left for the backend, and FIR-generated declarations are automatically converted into IR. GitHub

That's why this division works well:

FIR:
    User.metadata() exists
    return type = Metadata<User>

IR:
    here's what User.metadata() actually does

If you only generate something at the IR stage, you're too late for:

Kotlin
User.metadata()

because name resolution happens before IR.

Getting the exact IntelliJ gray preview

This part is good news: you don't have to implement that gray editor UI yourself.

What you're seeing is IntelliJ's "Generated by Kotlin compiler plugin" declaration inlay. JetBrains implemented this generic mechanism so Kotlin compiler-plugin-generated declarations can be rendered as those fake gray declarations. It became available in IntelliJ IDEA 2025.3. YouTrack

So if IntelliJ's Kotlin analyzer loads your FIR plugin and sees:

Kotlin
companion object {
    fun metadata(): Metadata<User>
}

the IDE can render something along the lines of:

Kotlin
@Validatable
data class User(...)

    ┌─────────────────────────────────────┐
    │ companion object {                  │
    │     fun metadata(): Metadata<User>  │
    │ }                                   │
    └─────────────────────────────────────┘

You do not need to write an IntelliJ InlayHintsProvider just for this.

The @Ignore in your serialization screenshot is also not something you need to reproduce; it's related to how the generated declaration is represented/rendered internally. There is even an IntelliJ issue specifically discussing the @Ignore shown in these generated-declaration inlays. YouTrack

The big catch: third-party compiler plugins in IntelliJ

This is currently the annoying part.

Kotlin's documentation says IntelliJ/Android Studio bundle their own development version of the Kotlin compiler, which is not necessarily binary-compatible with the released compiler. Because of that, community compiler plugins are not loaded by the IDE by default. Kotlin

For development, open IntelliJ's Registry and set:

kotlin.k2.only.bundled.compiler.plugins.enabled = false

That option currently defaults to enabled, meaning non-bundled compiler plugins are normally excluded. YouTrack

After doing that, with a compatible K2 compiler plugin, Gradle sync can make the compiler plugin available to IDEA's Kotlin analysis. Compiler-plugin developers have confirmed this setup allows generated declarations/autocomplete without separately implementing the declarations as an IntelliJ plugin, although it remains unstable. kotlinlang #announcements

The biggest problem is version compatibility. For example:

Project/compiler plugin:
Kotlin 2.x.y

IntelliJ Kotlin analyzer:
possibly 2.x.y-dev-xxxx

Those may be ABI-incompatible even if the versions look close. That's why serialization works so seamlessly: it's one of IntelliJ's bundled compiler plugins.

Therefore, for your plugin

I'd structure your project roughly as:

validatable/
├── validatable-annotations/
│   └── Validatable.kt
│
├── validatable-compiler-plugin/
│   ├── fir/
│   │   └── ValidatableDeclarationGenerator.kt
│   ├── ir/
│   │   └── ValidatableIrGenerationExtension.kt
│   ├── ValidatableFirRegistrar.kt
│   └── ValidatableCompilerPluginRegistrar.kt
│
└── validatable-gradle-plugin/
    └── ValidatableGradlePlugin.kt

Your Gradle plugin uses:

Kotlin
KotlinCompilerPluginSupportPlugin

to attach the compiler-plugin artifact to Kotlin compilations. That's also the mechanism used by the official compiler plugin template. GitHub

The resulting flow is:

Gradle
  │
  └── loads validatable compiler plugin
             │
             ├── FIR
             │    @Validatable
             │         ↓
             │    synthetic Companion
             │         ↓
             │    synthetic metadata()
             │
             └── IR
                  generates body

and IntelliJ K2:

Gradle import
     ↓
loads your FIR plugin
     ↓
Analysis API sees synthetic declarations
     ↓
completion works:
    User.metadata()
     ↓
"Generated by Kotlin compiler plugin" inlay
shows:
    companion object {
        fun metadata(): Metadata<User>
    }

That's the mechanism behind the screenshot. Kotlin+1

One important correction to your initial assumption

The serialization companion/function isn't merely an IntelliJ illusion. It doesn't exist in the source file, but the compiler really generates it. Serialization's own documentation says the generated companion effectively becomes part of the class ABI. GitHub

So for your API, I would deliberately model metadata() exactly the same way instead of trying to fake only the editor display.
